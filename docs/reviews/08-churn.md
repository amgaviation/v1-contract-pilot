# Churn review — retention surface audit

Scope: `app/(app)` outward. Code-level only; no Stripe/Supabase API calls made. Every citation below was read directly in this repo.

---

### [CRITICAL] Public promise of a pre-purge warning has no implementation anywhere in the codebase

- Where: `app/(marketing)/pricing/page.tsx:360`; `app/api/holds/run/route.ts` (whole file); `lib/email/send.ts` (whole file, only 5 call sites exist)
- Issue: The pricing page FAQ states as fact: *"The export works throughout, and we tell you before anything goes."* (`pricing/page.tsx:360`, inside the "What happens if I put my account on hold?" answer). This describes a proactive warning before the hold-expiry job permanently deletes an account's clients, trips, invoices, estimates, expenses and ledger (`supabase/migrations/20260818200000_monthly_hold.sql`'s `expire_hold`, run daily by `app/api/holds/run/route.ts` per `vercel.json`'s `0 3 * * *` cron). No such warning exists in code. `app/api/holds/run/route.ts` only `console.log`s/`console.error`s what it purged (lines 168-213) — nothing is emailed, and there is no in-app notification system at all (confirmed by grepping the whole tree for "notification": only Stripe-payment-status hits, no notification center/table). Exhaustively grepping every `sendEmail(` call site in the product turns up exactly five files — `lib/email/send-invoice.ts`, `lib/email/send-estimate.ts`, `lib/email/send.ts` itself, `app/api/stripe/webhook/route.ts`, and `app/api/stripe/connect-webhook/route.ts` — none of which fire on an approaching or completed hold expiry. The only place a pilot can learn their hold is about to lapse is by proactively opening Settings → Account while the hold is running and reading the static warning text in `app/(app)/settings/account-panel.tsx:117-122`. A pilot who put their account on hold specifically because they stopped opening the product for a season is the least likely person to be checking that tab.
- Fix: Either stop making the "we tell you before anything goes" claim on the pricing page, or build the warning it promises: a scheduled check (e.g. extending `api/holds/run` or a sibling job) that emails the owner at T-14/T-7/T-1 days before `hold_ends_at`, using the same `lib/email/platform-mail.ts` pattern already built for receipts/payment-failed mail.

### [CRITICAL] Cancellation is a single click with no save attempt, no reason capture, and no mention of the hold alternative

- Where: `app/(app)/settings/billing/billing-panel.tsx:687-707` (URL: `/settings/billing`); `app/(app)/settings/billing/billing-buttons.tsx:180-215`; `app/(app)/settings/billing/actions.ts:282-329`
- Issue: The entire cancel flow is: a "Cancel at period end" button (`billing-buttons.tsx`'s `CancelResumeButton`, a plain `<form action={formAction}>` with no `onClick` confirm, no modal, no `window.confirm`) whose submit calls `setCancelAtPeriodEnd`, which goes straight to `stripe.subscriptions.update(subscriptionId, { cancel_at_period_end: true })` (`actions.ts:313-315`) and redirects. There is no exit survey, no reason dropdown, no discount offer, no downgrade suggestion, and critically no mention that "Put your account on hold" exists as a milder alternative — that control lives on a completely different Settings tab (see next finding). The only copy shown next to the button is: *"Cancelling stops the next charge; you keep what you've paid for through the period. Then the account goes read-only… nothing is deleted."* (`billing-panel.tsx:690-694`). This is the exact "no cancel flow at all" failure mode the churn-prevention methodology names first under Common Mistakes: *"Instant cancel leaves money on the table. Even a simple survey + one offer saves 10-15%."* Note also that Stripe's own hosted billing portal (reachable via `openBillingPortal` in the same file) is bypassed entirely by this in-app button — even if the portal's own configurable cancellation flow has retention features turned on in the Stripe Dashboard, this product's primary cancel path routes around it.
- Fix: Insert a survey + dynamic offer step between the button click and the Stripe call: capture a reason (too expensive / not flying right now / missing a feature / other), and for "too expensive" or "not flying right now" branch to the existing Hold action (`placeHold` in `account-actions.ts`) before falling through to the current `setCancelAtPeriodEnd` behavior for anyone who still wants to leave.

### [CRITICAL] The one read-only banner shown on every page states "your subscription has ended" for statuses where it hasn't

- Where: `app/(app)/app-shell.tsx:340-355`; contrast `lib/billing-state.ts:68-121`; `lib/entitlements.ts:135,163-186`
- Issue: `AppLayout` (`app/(app)/layout.tsx:54`) computes one boolean, `accountIsReadOnly(account)`, and `AppShell` takes only `readOnly: boolean` (`app-shell.tsx:96`) — no status string, no reason. Every page in the product then renders the identical banner when that boolean is true: *"Your subscription has ended, so this account is read-only… Resubscribe to make changes again."* (`app-shell.tsx:342-353`). `accountIsReadOnly` returns true for six different underlying causes (`entitlements.ts:135` `ACCOUNT_WRITABLE_STATUSES = ["trialing","active"]`, plus `hold_started_at` and `deactivated_at`), and the subscription has genuinely *not* ended for most of them: `past_due` (Stripe is still retrying the card), `unpaid`, `incomplete`, and `paused`/hold (a pilot's own deliberate, resumable pause). "Resubscribe" is also the wrong instruction for `past_due`/`unpaid`/`incomplete` — those need a card update via the billing portal, not a new Checkout session (the `resubscribe()` action in `actions.ts:197-202` explicitly refuses to run on anything but `canceled`/`incomplete_expired`). The correct, status-specific language already exists in the codebase — `lib/billing-state.ts`'s `STATUS_DISPLAY` map gives an accurate sentence for every one of these statuses (e.g. `past_due`: *"your last payment didn't go through… Update your card in the billing portal and Stripe will retry."*, `paused`: *"This subscription is paused… Resume it from the billing portal…"*) — but that map is only read by the Billing page itself, never by the global banner. This is the single most-seen churn-relevant touchpoint in the product (rendered on every route under `app/(app)`), and for a pilot who is mid-dunning or who deliberately parked their account for the season, it currently tells them something false and alarms them into the wrong next action.
- Fix: Pass `account.status` (or the already-computed `statusDisplay(account.status)`) down to `AppShell` and render `meaning` from `lib/billing-state.ts` instead of the hardcoded string; keep a distinct sentence for the hold case (`hold_started_at` set) since it isn't a `status` value at all.

### [CRITICAL] The email-domain blocker is a single point of failure for every piece of dunning and receipt mail, with no fallback and no admin alerting

- Where: `README.md:74-79`; `lib/email/send.ts:14,111-134`; `app/api/stripe/webhook/route.ts:316-327,389-439`
- Issue: README's own Status section states: *"signup returns `Error sending confirmation email`… the send is rejected with `550 — the sending domain is not verified`… The same verification gates invoice email delivery."* (`README.md:74-79`). That verification gates far more than invoices: `lib/email/send.ts` is documented in its own header as *"THE ONLY PLACE THIS PRODUCT SENDS MAIL"* (line 14), reading the same `RESEND_API_KEY`/`INVOICE_FROM_EMAIL` pair for every caller. The platform-billing webhook's payment-failed and receipt emails (`buildSubscriptionPaymentFailed`, `buildSubscriptionReceipt` in `lib/email/platform-mail.ts`) are sent through this exact function (`app/api/stripe/webhook/route.ts:319-327,342-349`). The send is wrapped in `sendPlatformMailForSubscription`, which never throws and only `console.error`s a failure (lines 389-439, e.g. line 427-431) — so while the domain is unverified, every pilot whose card fails gets **zero notification of any kind**: no email (blocked at the Resend API), no in-app notification (none exists, see the finding above), nothing but the generic, currently-misleading banner from the previous finding once they happen to log back in. This is a single unresolved DNS/DKIM task silently disabling the entire involuntary-churn recovery path, and nothing in the product surfaces that it is disabled — the failure is a server-side log line only.
- Fix: Resolve the domain verification (or point `INVOICE_FROM_EMAIL` at `onboarding@resend.dev` temporarily, per README's own suggestion) before relying on any dunning email to reach a real pilot. Separately, promote a platform-mail send failure from a `console.error` to something operationally visible (e.g. a threshold alert), since today a full outage of this channel produces no signal anyone would see.

### [HIGH] The hold (pause) alternative is invisible from the page where cancellation actually happens

- Where: `app/(app)/settings/billing/billing-panel.tsx:687-707` (URL: `/settings/billing`) vs. `app/(app)/settings/account-panel.tsx:104-189` (URL: `/settings?tab=account`); `app/(app)/settings/settings-tabs.tsx:95-100,227-236`
- Issue: "Put your account on hold" — the exact, milder answer to "I don't want to pay for this right now" that the churn-prevention methodology recommends offering at cancel time — exists (`account-panel.tsx:145-189`) but lives on the "Account" tab, which `settings-tabs.tsx` renders last and outside every named group (`TAB_GROUPS` at lines 95-100 groups Billing under "Business" with Business/Payments; "Account" gets its own unlabeled trigger at lines 234-236, styled and positioned as the terminal "way out" section, deliberately after Profile & security). A pilot who goes to Billing to cancel — the natural, first place to look — sees nothing about Hold at all; they'd have to already know to browse to the very last tab in an entirely different group. `account-panel.tsx`'s own header comment even states the intended design: *"A pilot who arrives wanting to 'stop paying for this' meets DEACTIVATE first… The opposite order… converts 'I need a break this quarter' into a destroyed account"* (lines 21-28) — but this reasoning is only applied within the Account tab; it never reaches the pilot who starts from Billing.
- Fix: Surface a "Consider a hold instead" link/card directly beside the Cancel button in `billing-panel.tsx`, pointing at `/settings?tab=account`, before the pilot ever submits `setCancelAtPeriodEnd`.

### [HIGH] Two different "stop paying" flows exist with different financial consequences and no cross-link

- Where: `app/(app)/settings/billing/actions.ts:282-329` (`setCancelAtPeriodEnd`) vs. `app/(app)/settings/account-actions.ts:134-163,208-238` (`deactivateAccount`/`endSubscription`)
- Issue: Billing's "Cancel at period end" preserves the remainder of the paid period (`cancel_at_period_end: true`, no proration, subscription stays active until period end). Account's "Deactivate" calls `stripe.subscriptions.cancel()` **immediately** — the code's own comment states: *"Deactivating or deleting is a different sentence… leaving a live subscription attached to a deleted tenant would keep charging a card with nothing behind it. The UI says plainly that the rest of the period is not refunded."* (`account-actions.ts:134-141`). A pilot mid-way through a paid month who lands on Deactivate first (it is the first, mildest-looking card in the Account tab, immediately after Hold) forfeits days they already paid for that Cancel-at-period-end would have preserved — and neither screen tells them the other option exists or explains the financial difference.
- Fix: Add one sentence to the Deactivate card explicitly contrasting it with Billing's Cancel-at-period-end ("if you'd rather keep the days you've already paid for, cancel from Billing instead"), and vice versa.

### [HIGH] No dunning escalation, and no notice at all when Stripe finally cancels the subscription

- Where: `app/api/stripe/webhook/route.ts:265-301,303-329`; `lib/email/platform-mail.ts:87-113`
- Issue: `invoice.payment_failed` sends the exact same static template — *"V1 payment failed — update your card"* — on every retry Stripe attempts, with no escalating urgency between the first failure and the last (`buildSubscriptionPaymentFailed`, `platform-mail.ts:87-113`). Worse, the `customer.subscription.updated`/`customer.subscription.deleted` case (`webhook/route.ts:265-301`) — which is what fires when Stripe's dunning exhausts and the subscription moves to `unpaid` or `canceled` — calls only `syncSubscriptionState`; no email is built or sent for it anywhere in the handler. A pilot who ignores (or never receives, per the SPOF finding above) the payment-failed alert learns their subscription is actually gone only by logging back into the product and reading the read-only banner — which, per the finding above, currently tells them something inaccurate for several of the statuses that can produce this state.
- Fix: Add a `buildSubscriptionCanceledForNonPayment` template and send it from the `customer.subscription.updated`/`.deleted` branch when the incoming status is `unpaid` or `canceled` and the previous status was `past_due`/`unpaid` (i.e. this is dunning exhaustion, not a voluntary cancel). Escalate the payment-failed copy's tone using `nextAttemptIso` being null (final attempt) vs. present.

### [HIGH] No lifecycle or re-engagement email exists for the pilot at all, beyond a receipt and a payment-failure alert

- Where: grep of every `sendEmail(` call site: `lib/email/send-invoice.ts`, `lib/email/send-estimate.ts`, `lib/email/send.ts`, `app/api/stripe/webhook/route.ts`, `app/api/stripe/connect-webhook/route.ts` — no others exist in the repo; `app/api/reminders/run/route.ts:9-25` (scope: invoice reminders only)
- Issue: The task brief distinguishes `api/reminders/run` (invoice-due reminders the pilot sends to *their own clients*) from any lifecycle email to the pilot themselves — and confirms there is none. There is no usage-lapse nudge ("you haven't logged a trip in three weeks"), no expiring-document reminder (despite Documents having its own in-app "expiry ladder" per the site map — a medical or certificate about to lapse triggers no email, only an in-app badge someone has to be looking at), no win-back sequence after cancellation, and no card-expiring-soon proactive alert (only a reactive payment-*failed* alert after the fact). `vercel.json`'s only two crons are `/api/reminders/run` (client invoice chasing) and `/api/holds/run` (the purge job) — there is no scheduled job that could even drive a lifecycle email if the templates existed.
- Fix: At minimum, add a card-expiring-soon email (Stripe's subscription object and its default payment method's `exp_month`/`exp_year` are already available wherever `subscriptionFacts` is read in `lib/stripe/billing-facts.ts`) and a document-expiry digest reusing the same expiry computation `app/(app)/documents/page.tsx`'s ladder already does in-app.

### [MEDIUM] The payment-failed dunning email sends the pilot to the general billing page instead of Stripe's own one-click hosted invoice

- Where: `lib/email/platform-mail.ts:87-113` vs. `62-73`; `app/api/stripe/webhook/route.ts:319-327`
- Issue: `buildSubscriptionReceipt` (the success-path sibling in the same file) links its button to `input.hostedInvoiceUrl` when Stripe supplied one (lines 67-69), landing the pilot on Stripe's own hosted page for that invoice. `buildSubscriptionPaymentFailed` never receives or uses an equivalent URL — its button is hardcoded to `BILLING_URL` (`/settings/billing`, line 106) regardless of what the triggering invoice carries. The webhook handler already has the full `invoice` object in scope at the call site (`webhook/route.ts:303-311`) and could pass `invoice.hosted_invoice_url` the same way the success-path case does two cases later (line 347) — it simply doesn't. Dunning best practice (and this repo's own better half) is a direct one-click link to fix the specific failed charge; this email instead requires signing back into the product and finding the billing portal button.
- Fix: Add `hostedInvoiceUrl` to `SubscriptionFailureInput` and pass `invoice.hosted_invoice_url ?? null` from the webhook the same way the receipt case already does; prefer it over `BILLING_URL` when present.

### [MEDIUM] No early-warning signal or admin-facing health view exists anywhere in the product

- Where: repo-wide search — no `app/admin` (or similar) directory exists; no `last_active`/`last_sign_in`/`engagement_score`/`health_score`/`inactivity` column or field appears in any migration or app file outside auth's own `last_sign_in_at` display on the pilot's own Profile tab (`app/(app)/settings/page.tsx:439`, shown only to that one user, not aggregated anywhere)
- Issue: The task's methodology calls for tracking leading indicators (login frequency drop, feature-usage stop, billing-page-visit spikes) and a health-score model so an operator can intervene before a cancellation happens. None of the raw material is aggregated anywhere an operator could see it: there is no admin surface in the app at all, and no account-level "last active" or "days since last trip" column exists in the schema. The per-account data that would feed such a signal (last trip date, unbilled queue size — already computed for the Overview dashboard per the product-marketing digest) is never rolled up across accounts.
- Fix: Out of scope for a quick fix, but flagging per the brief: at minimum, add a `last_active_at` stamp on `pilot.accounts` (touched by `requireAccount()`) so a future admin view or scheduled digest has something to query against.

### [MEDIUM] Downgrade, Deactivate, Reset and Delete share Cancel's zero-reason-capture design

- Where: `app/(app)/settings/billing/billing-buttons.tsx:24-76` (`ChangePlanButtons`); `app/(app)/settings/account-panel.tsx:193-334` (Deactivate/Reset/Delete forms)
- Issue: Every downgrade tier button and every one of the three destructive account actions is a direct form submit straight to its server action — `changePlan`, `deactivateAccount`, `resetAccountData`, `deleteAccount` — none of which collect a reason or attempt an alternative first. This isn't isolated to Cancel (Finding above): it's the same pattern repeated four more times. A Business→Solo downgrade triggered by cost gets no "would a discount help?" moment; Delete gets only a password + typed business name, no "what made you decide this" capture that a founder or support team could ever learn from.
- Fix: At minimum, add a one-question reason capture (even a required free-text field, logged server-side) to `deleteAccount` and `changePlan`-when-downgrading — the two actions with the most retrievable signal about why a paying account is leaving or shrinking.

### [MEDIUM] Full account export excludes receipt and document image files from bulk download — exactly when a leaving pilot has the least patience for manual work

- Where: `app/(app)/settings/export/page.tsx:241-246` (URL: `/settings/export`)
- Issue: The export page's own closing note: *"Not included as files: receipt images and document scans (the CSVs record that a file exists; download each from its own page)…"* (lines 242-244). The CSV rows for Documents and Expenses record metadata and a filename only (`app/(app)/settings/export/entities.ts:1043-1069` `documentValues`, `941-979` `expenseValues`'s `yesNo(Boolean(row.receipt_path))`); the actual scanned PDF/image for each medical, certificate, insurance card, or receipt must be opened and downloaded one at a time from its own page. For a pilot with years of receipts and documents who is exporting specifically because they're about to cancel or let a hold lapse, this turns "take your data with you" — the product's own stated goodwill move (`account-panel.tsx:87-93`: *"Everything below is permanent… Download it first."*) — into a manual, multi-hundred-click chore at the exact moment goodwill matters most for a possible future win-back.
- Fix: Add a bulk zip download for receipt/document files (even a simple server-side zip stream keyed off `documents.file_path`/`expenses.receipt_path`), or at minimum surface a direct list of every file's individual download link on the export page itself instead of sending the pilot back into Documents/Expenses to find each one.

### [MEDIUM] The platform subscription's actual grace-period/dunning cadence is invisible to this codebase, and the one retry figure documented in-repo names a different mechanism

- Where: `docs/BILLING.md:152`; `app/api/stripe/webhook/route.ts:303-311`
- Issue: `docs/BILLING.md` states *"Stripe retries for up to 3 days"* (line 152) — but this sentence is about `pilot.stripe_events` idempotency, i.e. how long Stripe keeps re-delivering a **webhook** to this endpoint if it 5xxs, not how long Stripe's Smart Retries keep re-attempting a **failed subscription charge**. The latter — the actual grace period a `past_due` pilot has before the subscription becomes `unpaid`/`canceled` — is configured entirely in the Stripe Dashboard and does not appear anywhere in this repo. A future engineer reading only `docs/BILLING.md` could reasonably (and wrongly) conclude the payment grace period is 3 days. The webhook does correctly surface Stripe's real per-invoice `next_payment_attempt` in the failure email (`webhook/route.ts:322-326`), so the pilot sees an accurate date — but no document in the repo states the overall policy (how many attempts, over how long, before the account is lost).
- Fix: Document the Stripe Dashboard's actual Smart Retries schedule (attempt count and total window) in `docs/BILLING.md` next to the existing webhook-retry note, and clarify that the two "retry" concepts are unrelated.

### [LOW] Stale engineering comment claims no self-serve cancellation exists, contradicting shipped code

- Where: `app/(marketing)/terms/page.tsx:50-55` (URL: `/terms`)
- Issue: *"there is no self-serve cancellation path — 'cancel anytime' is not a claim this page makes."* This is contradicted by the shipped `setCancelAtPeriodEnd` (`settings/billing/actions.ts`) and `deactivateAccount` (`settings/account-actions.ts`), both real, user-facing, self-serve cancellation paths. The placeholder Terms page itself doesn't repeat this claim to visitors (it just says the real terms aren't published yet), so this isn't user-facing today — but it risks steering whoever drafts the real Terms of Service into under- or over-stating the pilot's cancellation rights.
- Fix: Update or remove the comment when the real Terms of Service copy is drafted, so it doesn't get carried forward as false context.
