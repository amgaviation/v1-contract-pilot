# Signup & activation-handoff review — app/(auth), app/auth/confirm

Scope: `app/(auth)/{login,signup,forgot-password,reset-password,check-email,link-expired,welcome}/**`
(pages, forms, and server actions), `app/(auth)/{auth-brand,auth-column,auth-parts,layout,loading,
resend-actions}.tsx`, `app/auth/confirm/route.ts`, plus the CTA→`/signup` handoff from
`app/(marketing)` read for continuity. Supporting libs read where a screen's behavior depends on
them: `lib/auth/{confirmation,signup-outcome}.ts`, `lib/password-policy.ts`, `lib/email/address.ts`,
`lib/safe-next.ts`, `lib/stripe/{server,prices,provisioning}.ts`, `lib/entitlements.ts`,
`lib/supabase/{account,proxy}.ts`, `components/ledger/{forms,segmented,index}.tsx`,
`app/design/ledger.css`. Per instructions, Discrepancy 3 (Resend domain unverified → signup's
`Error sending confirmation email`) is treated as a given, live blocker and not re-diagnosed;
findings below are its funnel consequences and the safeguards (present or missing) around it.
`node_modules` is not installed in this environment, so no framework-behavior claim below rests on
`node_modules/next/dist/docs/` — claims about Supabase Auth's server-side behavior during the mail-send
failure (Finding 1) were independently verified via the Supabase issue tracker/discussions (cited
inline) rather than assumed.

---

### [CRITICAL] The live confirmation-email failure is laundered into a false "nothing was saved," then a false "sent" — trapping every affected visitor with zero way out, permanently, not just during the current outage
- Where: `app/(auth)/signup/actions.ts:131,144` (`classifySignUpError` call and the message it returns to the form); `lib/auth/signup-outcome.ts:138-147` (the generic fallback branch); `app/(auth)/resend-actions.ts:119-137` (resend always reports success); `app/(auth)/check-email/check-email-view.tsx:49-51` ("Open the link we sent to… It works once and expires"); `lib/entitlements.ts:391-399` (no support channel exists anywhere in the product)
- Issue: Supabase Auth creates the `auth.users` row for a new signup *before* it attempts to send the confirmation mail; when that send fails (exactly Discrepancy 3's shape — SMTP/Resend rejects with 550), GoTrue returns the account call as a client-visible error (`status: 500`, `code: "unexpected_failure"`, message "Error sending confirmation email") while the unconfirmed user row persists server-side. This is documented, reported Supabase behavior, not speculation — see [supabase/auth#1388](https://github.com/supabase/auth/issues/1388), [supabase/supabase#20739](https://github.com/supabase/supabase/issues/20739), and the "ghost account" pattern described in [supabase/supabase#41590](https://github.com/orgs/supabase/discussions/41590): a repeat signup with the same address is thereafter treated as an existing account. `classifySignUpError` (`lib/auth/signup-outcome.ts`) has no case for this error shape — it isn't in `TAKEN_CODES` (`:70`), isn't `weak_password`, isn't a rate-limit or `email_address_invalid` code — so it falls through to the final branch (`:138-147`) and `signup/actions.ts:144` shows the pilot: *"We couldn't create your account just now, and nothing was saved. Try again in a moment."* That sentence is false for this specific failure: something *was* saved. Believing it, the pilot retries with the same email. On the second attempt, Supabase now returns its normal obfuscated "address already has an account" shape, which `classifySignUpError:93-95` correctly maps to `pending-confirmation` — but this silently sends them to `/check-email` (`signup/actions.ts:139`), which states as fact: *"Open the link we sent to [email]… It works once and expires"* (`check-email-view.tsx:50-51`). No mail was sent — the account is unconfirmed and the send path is still broken. If the pilot then clicks "Send it again," `resendConfirmation` (`resend-actions.ts`) calls `supabase.auth.resend()`, which fails the same way; the action logs the error (`:123`) but **unconditionally returns `{ error: null, sent: true }`** (`:137`) regardless of whether Supabase's call succeeded — so the UI reports success (`RESEND_SENT_MESSAGE`, "a new link is on its way") every single time, forever, no matter how many times they click it. The pilot is now looking at a product that has twice told them a link is coming and once told them their account creation failed — three different false statements, zero of them actionable — with, per `lib/entitlements.ts:395-399`'s own comment, no support address, contact route, or help link anywhere in the product to escalate to. This is not a symptom that disappears the moment the Resend domain is verified: any *future* transient failure at the mail step (provider outage, rate limit, DNS blip) will trigger this identical chain, because the defect is in the error classification and resend reporting, not in the current DNS state.
- Fix: Two independent, security-preserving changes. (1) In `classifySignUpError`, add a case that matches this failure shape (message containing "sending confirmation" / "sending" alongside `code: "unexpected_failure"`) and route it toward `/check-email` rather than the generic "nothing was saved" retry message — the account likely exists, so that is the honest next step, with copy that says a confirmation email could not be sent and to try "Send it again" shortly. This is safe to say plainly rather than genericize: an SMTP/relay failure is a systemic signal identical for every address attempted during the incident, not a per-address fact, so stating it does not reopen the account-enumeration hole the rest of this file is carefully built to close. (2) In `resendConfirmation`, stop reporting `sent: true` when `supabase.auth.resend()` itself errors with an infrastructure-class code (`unexpected_failure`, 5xx) as opposed to a per-address outcome — an infra failure is safe to disclose for the same reason. Independently of both: the `console.error` calls already at `signup/actions.ts:132` and `resend-actions.ts:123` capture exactly the signal needed to alert on a spike in this failure class operationally, closing the "invisible until a human happens to grep logs" gap without touching user-facing enumeration safety at all.

### [HIGH] Login's blanket "credentials didn't match" also fires for a correct password on an unconfirmed account — the first thing this cohort is likely to try, and it lies to them too
- Where: `app/(auth)/login/actions.ts:25-28`
- Issue: `signIn` maps every `signInWithPassword` error to one sentence: *"Those credentials didn't match. Check them and try again."* Supabase returns a distinct, well-known error for a correct password on an unconfirmed address (`email_not_confirmed`, 400) — this collapses into the same generic message. A pilot who typed their password correctly is told it's wrong. This is a standing gap independent of Discrepancy 3 (any pilot who signs up, gets a real confirmation email, and impatiently tries to log in before clicking it hits this today), and it compounds Finding 1 directly: a visitor currently stuck in the false "check your email" loop above will rationally try signing in with the credentials they just set — and be told those credentials are wrong, reinforcing the belief that something they did is broken rather than the product.
- Fix: Special-case `email_not_confirmed` with its own sentence and a link to resend the confirmation (routing through the same enumeration-safe `resendConfirmation` action, which already tolerates an address with no pending-signup cookie by accepting a typed one). This discloses only "this specific address needs confirming," which the pilot already knows since they are the one typing their own password — it is not a new enumeration surface for a stranger typing an address they don't own, because a wrong password on an unconfirmed account should still fall back to the generic message.

### [MEDIUM] Every pricing-tier CTA discards the tier (and interval) the pilot just chose
- Where: `app/(marketing)/pricing/page.tsx:137,185-186` (`TIER_ORDER.map(...)` — all three cards' "Start for $5" button is a bare `href="/signup"`, tier not threaded through); `app/(auth)/welcome/welcome-actions.tsx:58-61` (`firstAvailable` defaults to the first configured tier and `interval` always initializes to `"monthly"`); `lib/entitlements.ts:35` (`PLAN_TIERS = ["solo", "pro", "business"]`, so "first configured" is always Solo when all three are priced)
- Issue: `/pricing` presents three distinct cards (Solo, Pro, Business) with real price differentiation — Business alone carries "Two-seat minimum: {BUSINESS_MINIMUM_MONTHLY}/month covers both seats" (`pricing/page.tsx:156-160`). Every card's button is identical: `<NextLink href="/signup">`. Whichever card a pilot deliberately compares and clicks, they land on the same generic signup form, and at `/welcome` the plan picker always opens on Solo/Monthly (`welcome-actions.tsx:58-61`) regardless of what they clicked minutes earlier. A pilot who clicked Business because they need two seats has to notice the picker reset to Solo and manually reselect Business — the exact price expectation the task asked to trace from "set upstream" to "shown here" is not carried at all; it is discarded at the first hop and rebuilt from a hardcoded default.
- Fix: Carry the tier (and, if ever made selectable, interval) as a query param from each pricing card through `/signup` to `/welcome` (`?plan=business`), and have `WelcomePage`/`PlanPicker` read it to seed `tier`/`interval` state instead of always defaulting to the first configured tier and `"monthly"`.

### [MEDIUM] The one mandatory click every confirmation and reset link requires is a second page, hand-styled off the product's own brand tokens
- Where: `app/auth/confirm/route.ts:77-139` (`confirmPageHtml`), `:141-165` (GET renders it, does not verify), `:174-279` (POST, reached only by its submit, actually verifies)
- Issue: By design (documented at length in the route's own header, citing Supabase's own troubleshooting guidance on mail-scanner prefetch spending single-use tokens), every emailed confirmation or recovery link now opens an interstitial — *"One more click finishes this"* — before the token is verified; only the form's POST calls `verifyOtp`/`exchangeCodeForSession`. That reasoning is sound and out of scope to relitigate, but the execution has two separate, fixable costs. First, it is a genuine second full-page load and click inserted into literally every confirmation, on top of the mailbox context-switch already required — real, measurable added friction on the single highest-drop-off step in this funnel. Second, despite its own comment's claim of being *"on brand,"* it is not: the button is `background: #2a2a72` (`:120`) against the product's actual navy `--ledger-brand: #0b1f33` (`app/design/ledger.css:111`) — a visibly different, more purple-leaning blue — and the font stack is `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, Helvetica, Arial, sans-serif` (`:99`) rather than Archivo, the product's real display face. (The page background, `#fcfcfd`, does correctly match `THEME_COLOR` in `lib/brand.ts:48` — only the interactive color and typography drift.) The first thing a pilot sees after leaving their inbox mid-signup is a page that reads as a different, generic product before it hands them back to the real one.
- Fix: Keep the GET/POST split (the security property is real and worth the click), but pull the interstitial's button color and font-family from the same values `app/design/ledger.css` already defines (`#0b1f33`, Archivo with the existing system-font fallback stack) so the one unavoidable extra screen in this flow looks like a continuation of the product rather than a hand-off to something else.

### [MEDIUM] Post-checkout provisioning wait has no auto-recovery, only a manual "Refresh," with no cap and nowhere to escalate
- Where: `app/(auth)/welcome/page.tsx:44-63`
- Issue: After Stripe checkout succeeds, the pilot returns to `/welcome?checkout=complete` and — if the provisioning webhook hasn't landed yet — sees *"Payment confirmed. We're provisioning now, which usually takes a few seconds"* with a single plain link: `<a href="/welcome">Refresh</a>` (`:58-60`). There is no client-side poll, no automatic retry, and no change in messaging no matter how many times the pilot manually refreshes — a paid pilot whose webhook is genuinely slow or stuck sees the identical "usually takes a few seconds" sentence on refresh five, with no escalation path and (per `lib/entitlements.ts:395-399`, cited in Finding 1) no support contact anywhere in the product to fall back on. This is the moment of maximum sunk cost in the entire flow — a card has just been charged — and it is also the one with the thinnest recovery story.
- Fix: Add a short bounded client-side poll (a handful of attempts over ~20-30 seconds) before falling back to the manual link, and change the copy after repeated failed refreshes to something that acknowledges the wait is abnormal (e.g. "this is taking longer than usual; your payment succeeded — try again in a minute") rather than repeating "usually takes a few seconds" indefinitely.

### [LOW-MEDIUM] No password-visibility toggle anywhere in the flow
- Where: `components/ledger/forms.tsx:36-41` (`LInput`, a plain native `<input>` with no toggle affordance); used as `type="password"` at `app/(auth)/signup/signup-form.tsx:200-208`, `app/(auth)/login/login-form.tsx:42-51`, `app/(auth)/reset-password/reset-password-form.tsx:25-47` (two fields)
- Issue: Every password field in the flow — signup, login, and both fields on reset — is a bare masked input with no eye-icon/show toggle. Paste is not blocked (no `onPaste` handler anywhere), which is good, but a typo in a masked field with no visibility option is otherwise undetectable until a failed submit (login) or a failed subsequent login (signup, which has only one password field and no confirm field). Given the flow already routes a mistyped signup password through email confirmation and a Stripe checkout before the pilot would ever discover it at their first real login, the cost of an undetected typo here is unusually high for this specific product.
- Fix: Add a toggle button to `LInput` (or a small wrapper used only for password fields) that flips `type` between `password` and `text`, `aria-pressed` state included.

### [LOW-MEDIUM] Password length is enforced only after a full server round trip
- Where: `app/(auth)/signup/signup-form.tsx:199-209` (hint text "At least 8 characters," no `minLength`); `app/(auth)/reset-password/reset-password-form.tsx:25-36` (New password) and `:38-47` (Confirm new password) — neither field carries `minLength`; rule lives in `lib/password-policy.ts:26` (`MIN_PASSWORD_LENGTH = 8`)
- Issue: The 8-character floor is stated as static caption copy but never attached to the input as `minLength={8}`. A pilot who types a 5-character password gets no feedback until the full form submits, the server action runs, and `passwordProblem` (`lib/password-policy.ts`) rejects it — a full network round trip to catch something the browser could flag instantly, and on signup specifically the password field is not preserved across the failed submit (deliberately, per the form's own comment, since the password "is intentionally never echoed back"), so the pilot retypes it from scratch.
- Fix: Add `minLength={8}` to each password `<input>` alongside the existing hint text. This is purely additive to the existing server-side check (which must stay, since `minLength` is trivially bypassable) and costs nothing in security terms.

### [LOW] Two decision points in this flow use a touch target well under the product's own 44px floor
- Where: `components/ledger/segmented.tsx:121-126` (`px-3 py-1.5 text-body-s`); `app/design/ledger.css:234-236` (`--text-body-s: 0.84375rem`, `--text-body-s--line-height: 1.25rem`); contrast with `components/ledger/index.tsx:73` (`lg: "h-11 …"`, the 44px button size `auth-parts.tsx`'s own comment names as "the touch-target floor")
- Issue: `LSegmented` — used for the account-type toggle on `/signup` (`signup-form.tsx:169-179`) and the billing-interval toggle on `/welcome` (`welcome-actions.tsx:73-91`) — renders each option at `py-1.5` (6px top/bottom) around 20px line-height text: roughly 32px tall, against the 44px `SubmitButton` correctly uses everywhere else in the same forms. Both are real decision points (account kind seeds the account's `kind` column; billing interval decides whether the $5 intro applies at all), not decoration.
- Fix: Raise `LSegmented`'s vertical padding (e.g. `py-2.5`-`py-3` at this font size) to clear 44px, or increase the touch target via a taller hit area independent of the visible pill.

### [LOW] `autoFocus` on the first field of every auth screen risks an immediate mobile keyboard pop before the surrounding context is read
- Where: `app/(auth)/signup/signup-form.tsx:140` (`full_name`); `app/(auth)/login/login-form.tsx:34` (`email`); `app/(auth)/forgot-password/forgot-password-form.tsx:91` (`email`); `app/(auth)/link-expired/link-expired-view.tsx:110` (`email`); `app/(auth)/reset-password/reset-password-form.tsx:32` (`password`)
- Issue: Every one of these forms auto-focuses its first field on mount. Where the browser honors it, this opens the on-screen keyboard immediately on load, which on a phone can push page content (and, on `/signup` specifically, the "$5 for your first month" offer box that sits below the fields, `signup-form.tsx:215-223`) out of view before the visitor has read it. This is inconsistent across mobile browsers (some suppress programmatic focus-triggered keyboards on load), which is exactly why it is easy to miss in review and worth flagging rather than asserting as a guaranteed defect everywhere.
- Fix: Drop `autoFocus` on small viewports (a simple `matchMedia` check, or CSS-driven via a data attribute) while keeping it for desktop pointer users, where it costs nothing.

### [LOW] Re-signing up with an already-confirmed email silently discards the typed password and dead-ends at "check your email" for a message that will never arrive
- Where: `app/(auth)/signup/actions.ts:133-139` (the `pending-confirmation` branch, same destination for a brand-new signup and a taken address); `lib/auth/signup-outcome.ts:70,93-95` (`TAKEN_CODES`); `app/(auth)/check-email/check-email-view.tsx:69-71` ("Back to sign in" is the only way out)
- Issue: This is the deliberate, well-reasoned enumeration-safety design (documented at length in both files) working as intended, not a bug — but it is worth naming as the "already-registered email" edge path the task calls out. A pilot who forgets they already have a confirmed account and signs up again with the same address types a new password that is silently never applied to anything, is told nothing about why, and lands on `/check-email` waiting for a link that will not be sent (there is nothing left to confirm). The only way out is noticing the small "Back to sign in" footer link and guessing that is what happened.
- Fix: Nothing here should change the indistinguishability at the point of the `signUp` error (that protection is correctly load-bearing). Consider only a same-vagueness addition to `/check-email`'s copy — e.g., pairing the existing "Wrong address? Sign up again" line with an equally generic "Already have an account? Sign in instead" that is shown unconditionally on that screen (not conditionally on which case occurred) — which nudges the correct next step without disclosing which of the two cases the visitor is actually in.
